# I1 change plan: a checked evaluator for the reservation source

Status: APPROVED by the Owner on 2026-09-27, with every open question settled on the recommended option (Python 3.12 via uv; Prova value syntax for arguments; `evaluate` recorded as a proposed addition, SPEC.md not edited; `parse` refused as unavailable; bare `uv` on PATH). Binding for I1.

## Summary

The Owner gets a `prova` command that checks a `core-0` program as a whole and
directly evaluates its functions on fresh inputs and on their declared examples,
checking each call's precondition before the body and its postcondition against
the concrete result. Build, verify, format and parse are advertised as
unavailable and refused explicitly; no output ever says "verified", "proved" or
"built". Technically this is a new Python 3.12 package with no runtime
dependencies, a JSON request/response interface on stdin/stdout, and pytest
acceptance tests that drive only that public command.

## Changes by module

The repository has no code today, so every item below is new unless stated.

| Path | What and why |
|---|---|
| `pyproject.toml`, `uv.lock`, `.python-version` | Package `prova`, `requires-python = ">=3.12,<3.13"`, console script `prova`. No runtime dependencies. Dev group pins `pytest` and `hypothesis`. Lock committed so setup is reproducible offline. |
| `src/prova/reader.py` | UTF-8 s-expression reader: tokens, comments, integer literals (`[+-]?[0-9]+` to Python `int`), source spans (line/column) on every node. |
| `src/prova/syntax.py` | Typed syntax tree for the `core-0` grammar only, built from reader output. Anything outside the grammar (division, `defspec`, trailing top-level call, `Decimal`, text) is reported as `unsupported` or `syntax`, never as a type error. |
| `src/prova/checker.py` | Whole-program static checking per SPEC "Types, scope and composition": declaration collection, namespaces and uniqueness, no shadowing, nominal typing of every branch and clause (reached or not), arity, field selection, match exhaustiveness, acyclic type and call/contract graphs, example well-formedness. |
| `src/prova/evaluator.py` | Call-by-value evaluator with SPEC evaluation order and short-circuit `and`/`or`. Every user call (entry and nested, including calls inside contracts) evaluates `requires` before the body and `ensures` against the actual result. Integers are Python `int` end to end. |
| `src/prova/values.py` | Closed-value representation (Unit, Bool, Int, constructor with ordered named fields) and its canonical text rendering. |
| `src/prova/service.py` | Operation dispatch, manifest, response construction, diagnostics. The only place that knows operation names. |
| `src/prova/__main__.py` / console script | Reads one JSON request from stdin (or `--request FILE`), writes one JSON response to stdout. |
| `conformance/reservation.prova` | The reservation source, byte-identical to the SPEC.md code block (lines 523 to 567 at `d109daa`). |
| `conformance/variants/*.prova` | Hand-built wrong-body and invalid-program variants (Stories 2, 4, 5), each with a header comment naming the one thing changed. |
| `conformance/add-one.prova` | Small `core-0` source for Story 6. |
| `tests/acceptance/test_s<N>_*.py` | One file per story, invoking the installed `prova` command as a subprocess. No imports from `src/prova`. |
| `tests/properties/test_*.py` | Hypothesis properties (bounded, seeded), separate files from acceptance. |
| `tests/unit/` | Optional focused tests of internals; never the evidence for a story. |
| `docs/proposed-semantic-changes.md` | Records the one proposed vocabulary addition (the `evaluate` operation category, see Approach). |

### Interface (binding shape; exact field names fixed by fixtures in the first behaviour)

Request: `{"prova": "i1", "operation": "<op>", "source": "<program text>", ...}`.
Operations and their I1 status:

| Operation | I1 status |
|---|---|
| `discover` | Available: manifest of profile (`core-0`, partial), operations with availability, diagnostic categories, resource limits |
| `check` | Available: whole-program static check |
| `examples` | Available: runs every declared example, one result per function and example |
| `evaluate` | Available: one named function, argument values, one result |
| `parse`, `format`, `verify`, `build` | Refused, status `unavailable`, nothing attempted |

Response always carries `operation`, a `status` from SPEC's execution-status
vocabulary (`completed`, `unsupported`, `invalid_input`, `invalid_program`,
`resource_exhausted`, `tool_failure`, plus `unavailable` for refused operations),
a `claim` block stating kind (`evaluation` or `examples` or `static_check`) and
scope (this input, these examples), the source digest, and `diagnostics`, each with
a stable `category`, location (line/column and structural path) and reason.
Evaluation verdicts are distinct categories: `precondition_violation` (entry),
`call_precondition_violation` (nested), `postcondition_violation`, `malformed_value`,
`ill_typed_value`.

Values: argument values in requests are written in Prova's own `value` syntax
(`"(Reservation 1)"`, `"(Reserve)"`, `"9007199254740993"`), parsed by the same
reader. Results come back as canonical Prova value text plus a structured tree in
which integers are decimal strings. No JSON number ever carries a Prova integer,
so nothing passes through binary floating point.

Exit status: 0 whenever a well-formed response was written (including rejections
and refusals, which are results); non-zero only for tool failure or an unreadable
request.

## What deliberately will NOT change

- `SPEC.md`, `docs/EXPECTATIONS.md`, `evidence/` and the analyst's documents. The
  reservation source's semantics, contracts, examples and six-row table are
  protected; a disagreement is fixed in the implementation or raised to the Owner.
- No solver, SMT encoding, obligation inventory, `machine-0` descriptor, build
  backend or executable artefact. No format policy or syntax-tree interchange
  schema (hence `format` and `parse` refused).
- No historical fixture adaptation; `evidence/cases/` is not read by any test.
- No runtime dependencies; no network access at test time.
- No output wording "verified", "proved", "built" or "holds"; an acceptance check
  asserts this on every response.

## Approach & sequencing

Behaviours follow the story order (S1 to S6), each landing its checks and code
together:

1. **S1**: reader, syntax tree, the checker's positive path (enough to accept the
   reservation source), evaluator with contract checking, `evaluate`, `discover`,
   refusal of `build`/`verify`/`parse`/`format`. The protected-source byte-equality
   check lands here. Evaluation always runs static checking first and refuses an
   invalid program, so the evaluator never runs unchecked code.
2. **S2**: `examples` operation, per-function per-example results, one
   wrong-expected-value variant.
3. **S3**: entry decoding and precondition rejection, distinct `malformed_value`
   / `ill_typed_value` vs `precondition_violation`.
4. **S4**: three wrong-body variants under the unchanged contract.
5. **S5**: `check` operation exposed; checker rejection paths with category and
   location, including a type error in an unreached `step` branch and a second,
   different invalid construct.
6. **S6**: `add-one` source, large-integer evaluation, plus a seeded Hypothesis
   property over large positive and negative integers.

The one new abstraction is the evaluation operation. SPEC's category list has no
entry for fresh-input evaluation; S1 records it in
`docs/proposed-semantic-changes.md` as a proposed addition, without editing
SPEC.md.

## Risks & mitigations

- **Checker grows across stories.** Until S5, checking has only a positive
  control. Mitigation: S1 to S4 never claim checker rejection coverage; S5
  carries every rejection check, each paired with the unmodified source as the
  positive control.
- **Protected source drift.** Mitigation: an S1 acceptance check compares
  `conformance/reservation.prova` byte for byte with the SPEC.md code block.
- **Variant tests that pass for the wrong reason.** A wrong-body variant rejected
  by the checker, or by a precondition, would look like detection. Mitigation:
  each S4 check asserts the specific category `postcondition_violation`; since
  `evaluate` refuses an invalid program as `invalid_program`, that category also
  shows the variant passed static checking.
- **Honest labelling.** Mitigation: a shared acceptance assertion rejects the
  forbidden words in any response.
- **PATH for detached workers.** `uv` lives in `~/.local/bin`, which is not on the
  PATH a shell tool starts with on this machine. The runner image must put `uv`
  (0.11.x) on PATH; the coordinator's setup proof will show this in minutes if not.
  Python 3.12 is uv-managed; the system `/usr/bin/python3` is 3.9 and must not be
  used.
- **Offline verification.** Setup runs `uv sync --frozen`; evidence and test
  commands use `--no-sync` so no run needs the network after setup.
- **Evidence runner validation.** RELAY.md requires a passing, a failing, a
  missing-selector and a timeout case before dispatch. These are run by the
  coordinator against a throwaway check outside the committed suite; nothing
  deliberately failing is committed to `tests/`.
- **Engagement identity.** The Owner's condition on `prova-lang-v1` (ledger holds
  only this engagement) is a fact to check before dispatch, not something this
  plan resolves.
- No `risk-map.md` or `invariants.md` exists yet; there is no legacy code, so no
  characterisation tests are needed.

## Rejected alternatives

- Go or Rust bootstrap: needs a big-integer library and a second toolchain beside
  the pytest evidence stack, for no I1 benefit.
- JSON numbers for integers: loses exactness in many JSON clients.
- A flag-based CLI per operation instead of JSON requests: SPEC asks for a JSON
  service; flags can be added later as sugar over the same requests.
- Folding fresh-input evaluation into `examples`: hides a vocabulary change the
  analysis says must be recorded.
- Exposing `parse` with an ad hoc tree schema: SPEC requires the schema fixed by
  fixtures first; not needed by any I1 story.
- mutmut in the gate: extra dependency and runtime for little gain this iteration;
  S4's wrong-body variants are the targeted mutation evidence.
